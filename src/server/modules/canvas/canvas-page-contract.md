Create a report: a designed HTML page the user opens full screen, for depth a chat reply or a plan note cannot hold. Returns canvasId, title, path and sourcePath. Write the page into sourcePath, then call canvas_publish. This tool does not accept content directly. Before writing a report, load the `canvas-artifact` skill: it holds the design guidance. What follows is what the viewer does with the page, and what it will not do.

**What you write**: Only the page's content. The document around it is the viewer's, so begin the file with your own `<title>` and `<style>` and leave out `<!DOCTYPE>`, `<html>`, `<head>` and `<body>` (a whole document still renders, since the browser merges its tags into the skeleton, but canvas_publish warns). The head the viewer supplies holds a charset, a viewport meta with `viewport-fit=cover`, and a few base rules: `color-scheme: light` and safe-area padding above and below on `:root`, no body margin, a 14px system font, an off-white background, thin scrollbars in a grey that reads on a light or a dark page, `img{max-width:100%}` and `[hidden]{display:none!important}` (so show and hide with `el.hidden`; `style.display` cannot bring a hidden element back). Leave the `:root` padding in place. Whatever you pin to an edge allows for the insets itself: a fixed bar sits at `0` and pads itself by `env(safe-area-inset-top, 0px)` or `env(safe-area-inset-bottom, 0px)`, and a sticky header sits at `top: env(safe-area-inset-top, 0px)`.

**The name**: The report is listed in Reports, and headed in the viewer's bar, by its page's `<title>`. It is read from the first 8KB of the file at every canvas_publish; the `title` parameter stands in until a page has one. Name the report as you would name a document, usually in two to four words, or a few characters of Chinese or Japanese. Write it in the language the user writes in, and make it specific enough to find among many. Not a category that fits any report, and no subtitle after a dash or a colon. If a title has to lose a word, drop the generic one and keep the one that says what this is about; a title that is already one specific name needs no cutting. Do not rename a report from one publish to the next.

**What loads**:
- Scripts from other hosts: https://cdnjs.cloudflare.com (use it first), https://cdn.jsdelivr.net/npm/, https://unpkg.com, https://cdn.tailwindcss.com (the Tailwind play script) and https://code.jquery.com, and no others. Take a library's UMD build, which sets a global, pin its exact version, and put its tag before the inline script that uses it: `<script src="https://cdnjs.cloudflare.com/ajax/libs/<lib>/<exact version>/<file>">` (for React: react/18.3.1/umd/react.production.min.js, then react-dom).
- Stylesheets from other hosts: https://fonts.googleapis.com alone; its font files come from https://fonts.gstatic.com. Name a fallback family for every face.
- Nothing else comes from the network, and no error says so. Any other host is blocked (esm.sh among them), and the script hosts serve the page nothing but scripts: no stylesheets, images or media from them, no XHR or WebSockets, nothing a library fetches while it runs. `fetch()` is blocked everywhere, so the data a page needs goes in the page.
- Files beside index.html (in sourcePath's folder), by relative path: images, media, stylesheets and classic scripts load. Two things cannot come from that folder, fonts and ES modules: the sandboxed page requests them with CORS and the folder says no. So a font is embedded as a data: URI in @font-face, and a script is loaded by an ordinary `<script src>` and never as `type="module"`. All other CSS and JS goes inline.
- Linking to a file in the folder, say a PDF or a second HTML page, opens that file in a new tab under a tight sandbox: the PDF may come up blank and the HTML page will not run its scripts. What the reader needs belongs in the report itself.

**Links and leaving the page**: An `https://…` link opens in a new tab. `mailto:`, `tel:`, `sms:` and other app links may do nothing, and the page cannot find out whether they did: print the address or the number as text the reader can select (a copy button helps), and do not claim, on the strength of a tap, that a message was sent or a call begun. A download the page starts is dropped (`<a download>`, data: and blob: hrefs, a save from script), so offer no file that way. `alert()`, `confirm()` and `prompt()` show nothing: a confirmation is part of the page.

**Inside the frame**: The page runs in a sandboxed frame. Write for these limits rather than testing for them.
- Printing is unavailable: `window.print()` has no effect, so offer no Print or "Save as PDF" button.
- A form is part of the page's UI and has nowhere to submit to: take its `submit` event in script, call `preventDefault()`, and give it no `action` that points at a site or a mailto: address.
- To copy, call `navigator.clipboard.writeText` from inside the click handler. `navigator.clipboard` may be absent (Mandate reached from another device over plain http has none), so test for it first, catch a rejected call, and in either case fall back to selecting the text. The clipboard can never be read.
- No device APIs: location, camera, microphone, screen capture, Web Share and the rest.
- Fullscreen works from a click in a desktop browser and not on a phone: handle the refusal.
- Sound plays only once the reader has interacted (muted autoplay is allowed): start it from a button.
- No other site inside the page: no YouTube, map or form iframe, no `<object>` or `<embed>`. Link to it with an `<a href>`.
- A Web Worker starts only from a `blob:` URL: to the sandbox a worker file beside index.html is another origin, and it does not start. No service workers and no WebRTC.
- `localStorage` and `sessionStorage` are held in memory and gone when the report closes, so nothing the reader would miss should live only there.

**Size**: 16MB at most for the page, data: URIs included; files beside index.html are not counted. A larger publish is refused.

**Width**: The page has to read at a phone's width (about 400px) as well as a desktop's, and its body must never scroll sideways. Give `body` or one wrapper at least 16px of side padding, and set that element's vertical padding with `padding-block`, so that no `padding` shorthand zeroes the sides. Size things in relative units; let flex and grid rows wrap or fall to one column; hold images and `aspect-ratio` boxes to `max-width:100%`; use no `min-width` that exceeds the screen. A table, a diagram or a code block may be wider, inside its own `overflow-x: auto` box. A page that only makes sense wide (a dense dashboard, a large chart) may say so with `<meta name="viewport" content="width=1280">`, where the width is anything from 600 to 2560. The viewer then lays the page out that wide, shrinks it to fit the screen and lets the reader zoom. Use this only for a page that reflowing would ruin.

**Light and dark**: The viewer shows the page in its own theme, which reaches the page in one of three ways: `data-theme="light"` on the root element, `data-theme="dark"` on it, or neither (the "system" setting), when only `prefers-color-scheme` tells the two apart. Write for all three. Declare every color as a custom property on bare `:root` with its light value (a dark-first design does the same with the roles exchanged). Override the properties, and nothing but the properties, inside `@media (prefers-color-scheme: dark)` under `:root:not([data-theme="light"])`, and once more under `:root[data-theme="dark"]`, so that an explicit choice beats the system setting in both directions. Wherever the dark values apply, set `color-scheme: dark` as well (the skeleton sets `light` on `:root`), so that scrollbars and form controls match: in both dark blocks, or on bare `:root` for a dark-first or dark-only page. A color must never be defined only within a media query or a `[data-theme]` block. Give `body` a background from a token: behind the page the viewer draws a ground of its own, and a transparent body lets it through. A page that is one look on purpose may leave the dark blocks out, and still sets its background and every color itself.

**Content**: Put the conclusion first: the first screen answers what the reader came for, and the evidence follows. Write in the user's language; keep code, commands and identifiers as they are.

**Editing**: To change a report, edit sourcePath with the file tools; canvas_outline lists its top-level blocks and their size, canvas_remove_section drops one, and one canvas_publish renders the result. canvas_publish returns warnings for what it can see (a missing <title>, a blocked host, a body without a background, a token defined only in dark); fix them and publish again.
